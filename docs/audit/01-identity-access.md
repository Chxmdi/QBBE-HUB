## AUTH — identity and authorization

### AUTH-001 — Supabase Auth is the identity provider
**Verdict:** Complete
**Requirement:** Supabase Auth is the primary identity provider unless a later org-wide SSO decision supersedes it.
**Evidence:** All three clients are `@supabase/ssr`/`supabase-js` auth clients — `src/lib/supabase/server.ts:14`, `src/lib/supabase/client.ts:6`, `src/lib/supabase/middleware.ts:21`. Sign-in is `supabase.auth.signInWithPassword` (`src/app/(auth)/sign-in/sign-in-form.tsx:23`), sign-up is `supabase.auth.signUp` (`src/app/(auth)/sign-up/sign-up-form.tsx:38`), sign-out is a route handler at `src/app/auth/sign-out/route.ts`. Session refresh runs on every non-static request through the Next 16 proxy (`proxy.ts:4`, matcher at `:8-14`) calling `updateSession` (`src/lib/supabase/middleware.ts:13`). No competing identity provider exists: `grep` for `signInWithOAuth|signInWithOtp|sso` across `src/` returns nothing.

### AUTH-002 — Authorization modelled as membership, roles, scoped memberships, permissions
**Verdict:** Complete
**Requirement:** Authorization comes from organization membership, role assignments, scoped memberships and explicit permissions — not from email domain.
**Evidence:** `supabase/migrations/0001_core.sql:48-60` `organization_membership(organization_id, user_id, role org_role, status)`; `org_role` is a five-value enum at `:11`; `membership_status` at `:12`. Scoped memberships exist at every level: `team_member` (`:85`), `program_membership` (`:110`), `project_membership` (`:143`), `channel_member` (`supabase/migrations/0002_communication.sql`, with `role`/`is_mandatory`), `meeting_attendee`. Explicit per-channel permissions are columns on `channel` (`posting_policy`, `reply_policy`, `privacy`) consumed by `app.can_post_in_channel` (`supabase/migrations/20260902002201_scope_membership_join_policies.sql:51-69`). The application layer reads role from membership only (`src/lib/auth.ts:31-46`).
**Note:** No email-domain shortcut exists anywhere — `signup_allowed` (`supabase/migrations/0009_production_hardening.sql:3`) gates on an outstanding `invitation` row, not a domain. Verdict is Complete because the *representation* the requirement asks for is correct and complete; but see **AUTH-007**, where the provisioning path that populates this model grants an active `staff` membership to an uninvited self-registrant. The model is sound, the door into it is not.

### AUTH-003 — Object-level authorization on every query
**Verdict:** Partial
**Requirement:** Every request/query is authorized at object level; knowing a record ID must not grant access.
**Evidence:** The boundary is RLS, not the route. Request-path clients use the anon key only (`src/lib/supabase/server.ts:14-16`, `src/lib/supabase/client.ts:8-10`), so a `select ... eq('id', x)` is still filtered by policy. Deny-by-default is the stated convention (`supabase/migrations/0001_core.sql:3`) and every user-facing table carries `enable row level security`. Route guards (`requireStaff`, `requireAdmin` — `src/lib/auth.ts:66,73`) are explicitly documented as convenience gates on top of RLS, not the boundary. `supabase/tests/rls.sql` asserts the deny direction by ID for cross-organization rows (e.g. `:1288` "guest cannot read another organization task"), and runs in CI as the required `Database security` job (`.github/workflows/ci.yml:60,80`).
**Gap:** One live policy authorizes by role alone with no binding to the object — `"documents delete for staff"` (`supabase/migrations/0006_documents.sql:74-76`) is `bucket_id = 'documents' and app.is_staff()`, with no join to `document`. Any staff member **of any organization** can delete any object in the shared bucket given its path, which is exactly the failure mode this requirement names. `"documents upload for active members"` (`:70-72`) is unscoped the same way, though its blast radius is smaller. The read policy is fine: `0009_production_hardening.sql:58-69` joins to `document` and so inherits that table's organization-scoped read policy. See SEC-007 for why the scoping pass and its anti-regression assertion both missed these.

### AUTH-004 — Explicit policies on sensitive records
**Verdict:** Complete
**Requirement:** Private channels, leadership records, audit data and integration tokens each need explicit authorization policies.
**Evidence:** Private channels: `channel_read` admits a non-member only for `privacy = 'public'` within the same organization (`supabase/migrations/20260902002148_scope_remaining_policies_to_organization.sql:52-58`), and `message_read` delegates to `app.can_read_channel`, whose definer body carries the same test (`20260902002201:34-49`). Audit data: `audit_event` is admin-read, scoped to the row's organization (`supabase/migrations/20260818081240_scope_task_and_activity_policies_to_organization.sql:50-51`). Integration tokens: `integration_connection` is admin-only, organization-scoped (`supabase/migrations/20260818081500_scope_crm_reporting_integration_policies_to_organization.sql:32`), plus an owner-of-the-connection policy (`0008_spec_delivery.sql:82`); and the email ledger — recipient plus subject — is admin-only and organization-scoped (`20260902002148:104-107`). `supabase/tests/rls.sql` asserts the guest-denied direction on `email_delivery` (`:1268`), `workflow_execution` (`:1256`), `rate_limit_counter` (`:1279`) and the job queue (`:1302-1310`).
**Checked independently:** I enumerated every function in `public` and their grants, because a `SECURITY DEFINER` RPC granted to `authenticated` is the standard way an RLS boundary is bypassed without any policy looking wrong. There are none. All four RPCs reachable by `authenticated` — `global_search`, `approve_project_request`, `record_report_version`, `decide_report_version` — are **SECURITY INVOKER**, so they run under the caller's policies (`0005_search_deeplink_fix.sql:13`; `20260828160343:14-15`; `20260828163139:115,166`), and each of the decision RPCs additionally refuses a null `auth.uid()` up front (`20260828160343:22-25`, `20260828170831:18-19`). Every definer function is revoked from `public`/`anon`/`authenticated` and granted to `service_role` alone — `rate_limit_hit` (`20260822172945:75-76,93-94`), `count_export_download` (`20260828192352:24-26`), `email_orphaned_notifications` (`20260819165810:174-175`) — and the two remaining ones were deliberately narrowed with the reasoning recorded (`20260820180000_tighten_definer_grants.sql`). I also confirmed the table-level claim rather than taking it from the readiness docs: **75 `create table` statements, 75 `enable row level security`, no table missing it**, and exactly one `using (true)` policy in the whole schema — `retention_subject_read` on immutable reference data (`20260828200241:53-55`).
**Note:** HR/finance modules are named in the requirement as *future*; none exists, so there is nothing to police there yet.

### AUTH-005 — Service-role credentials are server-only
**Verdict:** Complete
**Requirement:** The service-role key is never exposed to the browser.
**Evidence:** `src/lib/supabase/service.ts:20` reads the key through `serviceRoleKey()` (`src/lib/env.ts:33`), an un-prefixed variable, so Next.js inlines it as `undefined` rather than leaking it if a client bundle ever imported it — the file says so at `env.ts:6-9`. Only `NEXT_PUBLIC_APP_URL`, `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` are public (`.env.example:8-15`). Every one of the ten `createSupabaseServiceClient` call sites is a route handler or a server service module; none is a `"use client"` file. `x-qbbe-actor: job-runner` is attached to its traffic (`service.ts:27`).
**Note:** The module's own contract comment (`service.ts:14-19`) says "only from `/api/jobs/*` handlers and the services they call" — and that is no longer true. It is also used by `src/app/api/exports/[id]/download/route.ts:70`, `src/features/admin/services/admin.commands.ts:143`, `src/features/inbox/services/gmail.commands.ts:34,93` and `src/features/calendar/services/google-calendar-write.ts:85,132,173`, all reachable from user-controlled requests. The requirement as written (never in the browser) is still met; the comment is stale and understates how widely the RLS bypass is reachable. The export route is the model to copy — it authorizes with the *user's* client first and uses the service role only to mint the signed URL (`download/route.ts:41-46,70`).

### AUTH-006 — MFA for admin/owner; documented account recovery
**Verdict:** Partial
**Requirement:** Owner/admin accounts use MFA before production rollout, and account recovery is documented and controlled by QBBE.
**Evidence:** MFA is carried as an explicit operator step — `docs/runbooks/deployment.md:35-36` ("Turn on MFA for the Primary Owner and Workspace Admin accounts (AUTH-006)"), tracked on the launch gate (`docs/runbooks/launch-gate.md:14`) and re-checked in the privacy review (`docs/runbooks/privacy.md:33`). It is a Supabase project setting, so there is nothing in this repository to enforce it; `docs/runbooks/launch-gate.md:31` honestly records the production project as **Not verified**.
Account recovery **is** documented, contrary to what the readiness docs imply: `docs/runbooks/backup-recovery.md:29-31` gives the admin-lockout path ("a second Workspace Admin or the Primary Owner restores access; Supabase org owners can reset auth. Keep >=2 trusted admins at all times (ENV-002)"), and `:22-27` covers losing the Supabase project or the deployment. Reactivating a deactivated member is a separate documented path (`privacy.md:10`) with a working control (`admin.commands.ts:107-158`).
**Gap:** Two holes rather than an absence. (1) **Lost MFA factor has no procedure** — the moment MFA is turned on per `deployment.md:35`, "keep two admins" stops being sufficient if the same person holds both factors, and nothing names who at QBBE holds a break-glass credential. (2) The application has **no self-service password reset**: `grep -rn "resetPassword|forgot" src/` returns nothing and neither auth form offers the link, so every forgotten password is a Supabase dashboard action by whoever holds the project. **What would settle it:** MFA confirmed enabled in the production Supabase project (`launch-gate.md:31` records it as Not verified), plus a lost-factor paragraph in `backup-recovery.md`.

### AUTH-007 — Invitation record shape and audit evidence
**Verdict:** Partial
**Requirement:** An invitation carries expiration, inviter, target email, intended role/team, `accepted_at`, `revoked_at`, and audit evidence.
**Evidence:** `supabase/migrations/0001_core.sql:62-74` — `invitation(organization_id, email, intended_role, invited_by, token, expires_at default now() + 14 days, accepted_at, revoked_at, created_at)`. Creation is admin-gated and rate-limited (`src/features/admin/services/admin.commands.ts:26-28`) and writes an `audit_event` with `action: "user_invited"` and the email + intended role in metadata (`:48-57`). Revoke sets `revoked_at` and refuses an already-accepted invitation via `.is("accepted_at", null)` (`:161-168`). Acceptance is closed by the signup trigger, which honours only a non-accepted, non-revoked, unexpired invitation (`supabase/migrations/0003_operations.sql:376-385`) and gates open signup through `signup_allowed` (`0009_production_hardening.sql:3-21`). The table is admin-only and organization-scoped (`20260818080439:114`).
**Gap:** Three things, the first of them serious.

**(1) The invite-only gate is enforced only in the browser.** `signup_allowed` (`supabase/migrations/0009_production_hardening.sql:3-19`) is correct, and it is called — from `src/app/(auth)/sign-up/sign-up-form.tsx:23-35`, a `"use client"` component, before `supabase.auth.signUp`. Nothing on the server repeats the check. `app.handle_new_user()` (`supabase/migrations/0003_operations.sql:336-408`), the `after insert on auth.users` trigger that actually provisions access, **never calls `signup_allowed`**: when it finds no matching invitation it falls through to `case when exists (select 1 from organization_membership) then 'staff' else 'owner' end` (`:381-383`) and inserts an **active** membership at that role (`:387-389`). So a direct `auth.signUp` against the public project URL with the public anon key — no invitation, no admin involved — yields an active **staff** account: projects, programs, CRM, reports, every task and every public channel. The `before_user_created` auth hook, which is exactly the server-side place for this check, sits commented out in `supabase/config.toml:284-287`, and `enable_signup = true` at `:182` and `:227`.

Two things make this worse than the mechanics alone. `docs/runbooks/deployment.md:24-26` tells the operator "either disable public signup ... or restrict to invited emails. **The app also enforces invite-only via `signup_allowed`**" — the reassurance is false, and an operator who believes it may reasonably leave signup open. And `supabase/tests/rls.sql:1313-1317` asserts `signup_allowed('nobody@example.com') = false`, which proves the *function* answers correctly and proves nothing about whether anything consults it — a green assertion sitting directly over the gap, which is the failure mode this project has been bitten by before. **What would settle it:** enable the `before_user_created` hook against `signup_allowed`, or have the trigger refuse a membership when no valid invitation exists; either way the assertion should test the provisioning path, not the predicate.

**(2) Intended team is absent** — the table has `intended_role` but no team column, and `inviteSchema` (`admin.commands.ts:10-13`) accepts only email and role, so an invitee cannot be pre-placed on a team. **(3) Revocation is not audited.** `revokeInvitation` (`:161-172`) writes no `audit_event`, unlike invite, role change, deactivate and ownership transfer around it — so "who cancelled that invitation" is unanswerable. Note also `inviteUser` always returns `emailSent: false` (`:61`): the invitation is a database row, and nothing emails the invitee.

## SEC — security baseline

### SEC-001 — OWASP ASVS-style verification baseline
**Verdict:** Missing
**Requirement:** Adopt an ASVS-style verification baseline covering authentication, authorization, input handling, session behaviour, file uploads, secrets, logging and data protection.
**Evidence:** `grep -rni "asvs|owasp"` across `docs/`, `src/` and `.github/` returns **zero** hits. There is no verification checklist keyed to those eight areas, no ASVS level chosen, and no per-release security sign-off artefact. The closest existing document is `docs/runbooks/launch-gate.md`, which is a launch checklist covering MFA, backups, privacy and integrations — useful, but not a verification standard and not organised by the ASVS chapters the requirement names.
**Gap:** The individual controls SEC-002..010 are largely present (see below), which is what makes this a documentation gap rather than a security one: the practices exist but nothing states the baseline they are being verified against, so nobody can say which requirements were checked at which release. **What would settle it:** an ASVS L1/L2 checklist in `docs/runbooks/` mapping each chapter to the control and test that satisfies it.

### SEC-002 — Server-side validation and sanitization of untrusted input
**Verdict:** Partial
**Requirement:** All untrusted input is validated and sanitized server-side; rich text, filenames, URLs, webhooks, imported email metadata and file uploads need explicit validation.
**Evidence:** Zod is the standard and is applied at the server-action boundary, not the form — **25 modules** import it, with 7 dedicated `schemas.ts` files; every command re-parses its input inside `"use server"` (e.g. `src/features/admin/services/admin.commands.ts:30-34`, `src/features/documents/services/document.commands.ts:72-75`) and bulk operations are capped server-side. Rich text is not a risk here because nothing renders user HTML: `dangerouslySetInnerHTML` appears exactly once, on a constant theme script (`src/app/layout.tsx:36`). Outbound email escapes every interpolated value (`src/features/notifications/services/email-templates.ts:53-58`) and refuses stored absolute/protocol-relative links via `safeLink` (`:67-72`). The Gmail webhook is genuinely verified before the body is parsed: the bearer token is presented to Google's `tokeninfo` endpoint, which establishes signature and issuer, and the returned claims are then checked locally for `aud`, the exact service-account `email`, `email_verified` and a future `exp` (`src/app/api/integrations/gmail/push/route.ts:7-21`, `src/features/inbox/services/gmail-sync.ts:19-32`); an unauthenticated request is rejected at `route.ts:26` before any work, and the base64 envelope is then bounds-checked (`gmail-sync.ts:41-52`). The audience and service-account values are required, so a missing environment variable fails closed rather than open (`gmail-sync.ts:26`).
**Gap:** **File upload validation is client-side only.** `src/features/documents/components/document-upload-dialog.tsx` enforces the 25 MB cap (`:19,53`), sanitizes the filename (`:63`) and picks the storage path (`:64`) *in the browser*, then uploads straight to storage with the anon key (`:65-67`). The server action that follows, `registerUploadedDocument` (`document.commands.ts:68`), accepts `storagePath`, `mimeType` and `sizeBytes` as client-supplied facts and writes them to the row — so the recorded size and type need not match the object, and neither the size cap nor the filename rule is re-checked anywhere server-side. `supabase/migrations/0006_documents.sql:62-77` creates the bucket and its policies but sets no `file_size_limit` or `allowed_mime_types`. **What would settle the remaining doubt:** either bucket-level limits, or a server-side `storage.getObject` head check in `registerUploadedDocument`.

### SEC-003 — HTTPS only, secure cookies, strict OAuth redirects, no secrets in query strings
**Verdict:** Partial
**Requirement:** HTTPS-only in shared environments, secure cookie/session settings, strict redirect allowlists for OAuth, and no secrets in query strings.
**Evidence:** HSTS is set for two years with `includeSubDomains; preload` on every response (`next.config.ts:11-14`), alongside `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy` and a `Permissions-Policy` (`:4-10`). The OAuth state cookie is `httpOnly`, `sameSite: lax`, `secure` in production, path-scoped and expires in 10 minutes (`src/app/api/integrations/google/start/route.ts:42-48`); the callback verifies state equality *and* that the state's embedded user matches the signed-in user (`callback/route.ts:22-32`) before exchanging the code, and its own redirect targets are three fixed in-app paths (`:207`). `redirect_uri` is a single environment-pinned value, never taken from the request (`start/route.ts:50`). The Supabase email-confirmation callback validates its `next` parameter explicitly — `startsWith("/") && !startsWith("//")` (`src/app/auth/callback/route.ts:9-12`). Job endpoints authenticate with an `x-job-secret` **header**, not a query parameter (`.env.example:56`), and outbound email links are forced back to in-app paths by `safeLink`.
**Gap:** Two, both found by checking rather than reading.

**(a) The session cookie itself carries neither `secure` nor `httpOnly`.** The app never passes `cookieOptions` — `grep -rn "cookieOptions" src/` returns nothing — so `@supabase/ssr` writes the auth cookies with its own defaults, which are `{path: "/", sameSite: "lax", httpOnly: false, maxAge: 400 days}` and **no `secure` flag** (`node_modules/@supabase/ssr/dist/main/utils/constants.js:4-11`). `httpOnly: false` is inherent to the library — the browser client has to read the session — but `secure` is not, and the app demonstrates it knows how by setting it explicitly on its own OAuth state cookie (`src/app/api/integrations/google/start/route.ts:45`). In practice HSTS (`next.config.ts:11-14`) plus HTTPS-only hosting closes the exposure after a first visit, so this is a defence-in-depth gap rather than a live one; but the requirement asks for secure cookie/session settings and they are defaults, not settings. Passing `cookieOptions: { secure: process.env.NODE_ENV === "production" }` to `createServerClient` is the whole fix. The 400-day `maxAge` is also longer than a charity workspace needs and is not a deliberate choice anywhere.

**(b) One open-redirect hole**, in the one place that skipped the check the codebase already knows how to write. `src/app/(auth)/sign-in/sign-in-form.tsx:36` does `router.push(searchParams.get("next") ?? "/")` with **no validation** — `/sign-in?next=https://example.com` navigates off-site after a successful sign-in. The middleware only ever sets `next` to a same-origin pathname (`src/lib/supabase/middleware.ts:53`), but nothing stops an attacker supplying the URL. The fix is the two-line guard already present at `auth/callback/route.ts:10-12`.

### SEC-004 — Rate-limit abuse-sensitive endpoints
**Verdict:** Partial
**Requirement:** Rate-limit or otherwise protect sign-in, invitations, search, message posting, file upload, exports, webhooks and workflow execution.
**Evidence:** A real limiter exists and is the right shape for a serverless deployment — counters in Postgres via `rate_limit_hit` (`supabase/migrations/20260822172945_rate_limiting.sql:39`) rather than in-process, with a documented fail-open policy and a structured log line when it degrades (`src/lib/rate-limit.ts:78-92`). Eight named ceilings (`:38-49`), exports deliberately the tightest at 10/hour. Applied at: invitations (`admin.commands.ts:27`), message posting (`message.commands.ts:28`), task creation (`task.commands.ts:30`), announcement publish (`announcement.commands.ts:53`), report generation (`report.commands.ts:28,102`), exports (`export.commands.ts:26`) and the job endpoint (`src/app/api/jobs/[job]/route.ts:63`). Sign-in is a documented, defensible exclusion: the browser talks to Supabase Auth directly, which applies its own limits (`rate-limit.ts:16-17`).
**Gap:** Three of the named endpoints are unprotected. (1) **File upload** — the `document:upload` limit is applied to `createDocumentLink` (`document.commands.ts:24`), the *link* path, while `registerUploadedDocument` (`:68-76`), the path that actually puts bytes in the bucket, has no limit at all. The name says upload; the placement says link. (2) **Search** has no limiter and no service module to hold one (`src/features/search/` contains only `result-types.ts`). (3) **The Gmail webhook** (`src/app/api/integrations/gmail/push/route.ts`) is unlimited — authenticated, so not anonymous abuse, but it writes on every delivery. Workflow execution is limited only indirectly, through `job:run`.
**Checked independently:** the limiter's fail-open path is wider than the comment implies. `checkRateLimit` obtains its client with `createSupabaseServiceClient()` (`src/lib/rate-limit.ts:59`), which calls `serviceRoleKey()` and **throws** when `SUPABASE_SERVICE_ROLE_KEY` is unset (`src/lib/env.ts:23-26,33`); that throw lands in the same `catch` as a transient database error and returns `allowed: true, degraded: true` (`rate-limit.ts:78-92`). So in any deployment missing that one variable, every rate limit in the product is silently off — the only signal is a `rate_limit.unavailable` line in the platform log, which nothing alerts on. Failing open is the right call for a transient outage; failing open permanently on a missing configuration is a different thing, and the two are indistinguishable from the outside. Admin → Jobs surfaces scheduler misconfiguration prominently; nothing surfaces this one.

### SEC-005 — Audit coverage for security-relevant events
**Verdict:** Partial
**Requirement:** Audit login/auth changes, role/permission changes, admin actions, channel-policy changes, integration connect/disconnect, sensitive-data exports, destructive actions and security-relevant failures.
**Evidence:** `audit_event` (`supabase/migrations/0001_core.sql:272`) is admin-read, organization-scoped, and written from ~27 sites. Covered by name: account provisioning at sign-up, written by the database trigger itself so it cannot be skipped (`supabase/migrations/0003_operations.sql:399`); `user_invited`, `role_changed`, `user_deactivated`/`user_reactivated`, `ownership_transferred` (`admin.commands.ts:53,99,154,227`); `channel_created`, `channel_member_added`, `channel_archived`/`channel_restored`, `message_pinned`, `message_deleted` (`channel.commands.ts:70,168,215`, `message.commands.ts:365,403`); `document_uploaded`, `document_downloaded`, `document_archived` (`document.commands.ts:100,141,162`); `export_requested`, `export_downloaded`, `report_generated`, `report_regenerated`, `report_exported_csv`, `report_exported_pdf`; `integration_disconnected` and `vms_connected` (`integration.commands.ts:62,140`); `project_closed`, `stage_changed`.
**Gap:** Four named categories are thin or absent. (1) **Login is not audited** — the only `auth` event is `user_provisioned` at first sign-up; there is no sign-in, sign-out or failed-sign-in record, because authentication happens browser-to-Supabase and nothing mirrors it into `audit_event`. (2) **Google integration *connect* is not audited** — `src/app/api/integrations/google/callback/route.ts` writes no `audit_event`, so Gmail/Calendar/Drive disconnects are recorded but the connections that granted the scopes are not; only the VMS path audits both directions. (3) **Channel *policy* changes are not audited** — creation and archive are, but there is no command that changes `privacy`, `posting_policy` or `reply_policy` after creation at all (see P0-ADM-02), so there is nothing to record. (4) **Security-relevant failures are not audited** — `grep` for `event_type: "security"` returns zero; a rate-limit trip logs to stdout (`src/lib/rate-limit.ts:79-86`) and a rejected webhook returns 401 silently. Invitation revocation is also unaudited (see AUTH-007).

### SEC-006 — No secrets or personal content in telemetry
**Verdict:** Partial
**Requirement:** Do not log passwords, tokens, secrets, message bodies, email bodies or unnecessary personal information in application telemetry.

Only **13** non-test `console.*` sites exist in `src/`; most emit structured JSON with an event name, an id and a message — no bodies (e.g. `src/app/api/jobs/[job]/route.ts:89`, `drain-notifications.ts:541,555`, `rate-limit.ts:81`). ### SEC-007 — Private files use access-controlled storage and signed retrieval
**Verdict:** Partial
**Requirement:** Private files live in access-controlled storage with signed/authorized retrieval; an obscure public URL is never the authorization.
**Evidence:** Both buckets are created with `public = false` — `documents` (`supabase/migrations/0006_documents.sql:62-64`) and `exports` (`20260828182304_export_jobs.sql:127-129`). These three are the only `storage.objects` policies in the repository, and they were missed by both scoping migrations. The anti-regression assertion cannot catch them either: it filters `pg_policies` on `schemaname = 'public'` (`supabase/tests/rls.sql:1342`), and these live in `storage`. Widening that predicate to include `storage` is a one-line change that would have surfaced this.

### SEC-009 — Dependency/security scanning in CI, findings reviewed before release
**Verdict:** Partial
**Requirement:** Run dependency/security scanning in CI and review high/critical findings before merge or release.
**Evidence:** Two scanners run on every push and pull request. `npm audit --audit-level=high` is a build step, so a high or critical advisory fails the job (`.github/workflows/ci.yml:58-59`) — verified here: it currently reports **0 vulnerabilities**. ### SEC-010 — Content-security and related browser headers
**Verdict:** Complete
**Requirement:** Use CSP and related browser headers appropriate to the deployment, especially around embedded external content and OAuth/integration pages.
**Evidence:** `next.config.ts:3-28` sets six headers on `/(.*)` (`:33-40`): a real CSP with `default-src 'self'`, `frame-ancestors 'none'`, `base-uri 'self'` and `form-action 'self'`; `connect-src` enumerated rather than wildcarded — Supabase (https + wss), the local dev stack, and exactly the Google endpoints the integrations call (`accounts.google.com`, `oauth2.googleapis.com`, `gmail.googleapis.com`, `www.googleapis.com`) plus the Sentry ingest host. ## P0/P1-GOV — channel governance

### P0-GOV-01 — Posting permissions, configured separately from replies
**Verdict:** Partial
**Requirement:** A channel owner/admin can restrict top-level posting **by role or by user**, and configure reply behaviour separately.
**Evidence:** The two are genuinely separate predicates, which is the substantive half of the requirement. Top-level posting goes through `app.can_post_in_channel` — member of the channel, channel not archived, and the role test the `posting_policy` names (`supabase/migrations/20260902002201_scope_membership_join_policies.sql:51-69`, now scoped to the channel's organization). Replies go through `app.can_reply_in_channel`, which deliberately does **not** apply `posting_policy`, so a member may reply in a channel whose top-level posting is admins-only (`0002_communication.sql:248-262`, with the reasoning in the comment at `:247-249`). The UI mirrors the database rather than replacing it: `canPost` is recomputed server-side (`src/app/(workspace)/channels/[id]/page.tsx:93-100`), a specific hint explains *why* posting is closed (`:102-108`), the header shows a "Restricted posting" badge (`:125-127`), and `replyPolicy` disables the reply affordance (`src/features/channels/components/channel-view.tsx:342,403`).
**Gap:** Three. (1) **Restriction by role only, never by user** — `posting_policy` is a three-value enum `everyone | staff | admins` (`0002_communication.sql:10`); there is no per-user allow/deny list and no column that could hold one, so "restrict top-level posting by ... user" is unimplementable as modelled. (2) **Neither setting can be changed after creation** — `posting_policy` is set once by `createChannel` and `reply_policy` is never set at all, so every channel takes the `'normal'` default (see P0-ADM-02). (3) **`threads_only` is enforced only in the browser.** `app.can_reply_in_channel` tests `reply_policy <> 'disabled'` (`:258`) and nothing tests `'normal'` vs `'threads_only'`; the distinction lives in `channel-view.tsx:342` alone, so a direct insert honours `disabled` but not `threads_only`. The requirement's authorization boundary is the database, and one of the three reply modes does not reach it.

### P0-GOV-02 — Private channel membership; removal cuts access on every path
**Verdict:** Partial
**Requirement:** Private channel membership is explicit or policy-driven, and removing access **immediately** prevents message and file retrieval **through all paths**.
**Evidence:** The enforcement half is genuinely thorough, and the side paths have been closed one at a time rather than assumed. `message_read` admits a channel message only via `app.can_read_channel` (`supabase/migrations/0002_communication.sql:348-351`), whose definer body requires `privacy = 'public'` in your own organization *or* channel membership (`20260902002201:34-49`). Because it is a `SELECT` policy on `message`, every derived path inherits it rather than re-implementing it: search is `security invoker` in all three of its migrations (`0005_search_deeplink_fix.sql:13`, `20260827164411:43`, `20260827172348:24`), so it runs under the caller's policies; saved messages became read-own with an insert-time visibility check (`0010_saved_messages_security.sql:5-17`); mentions were narrowed to own-mention-or-message-visible (`20260818074303:6-16`); reactions were reduced to "visible exactly when the message is" (`20260902002148:143-146`). Membership is explicit, and the join/leave/insert policies are now scoped to the channel's organization (`20260902002201:71-113`). Removal is immediate because the check is evaluated per query, not cached.
**Gap:** Two, both on the *membership* side rather than the enforcement side. (1) **There is no way to remove someone from a channel.** Every `channel_member` write in `src/` is an insert or a self-delete — `leaveChannel` (`channel.commands.ts:100-120`) filters `.eq("user_id", session.userId)`, and no command or UI removes another person, even though the RLS policy would permit an organization admin to (`20260902002201:100-113`). "Removing access" is a database capability with no product path. (2) **Policy-driven membership does not track the policy.** `createTeam` provisions a private team channel but adds only its creator (`team.commands.ts:41-56`); `addTeamMember` writes `team_member` alone (`:65-78`) and `removeTeamMember` deletes from `team_member` alone (`:84-99`) — neither touches `channel_member`. So joining a team does not grant its channel, and **leaving a team does not revoke it**: a person removed from a team keeps reading that team's private channel indefinitely. `membership_source` (`0002_communication.sql:46`) records the intent that this should be derived; nothing maintains it.
**Note:** One residual metadata leak, small but real: `mention_read` still admits `mentioned_user_id = auth.uid()` unconditionally (`20260818074303:10`), so someone removed from a private channel can still see that a mention row exists for them. `message_mention` holds only ids and a timestamp (`0002_communication.sql:116-121`), so no content escapes — but the fact of a mention does.

### P0-GOV-03 — Moderation actions with audit history
**Verdict:** Partial
**Requirement:** Authorized moderators can pin, archive, lock, remove prohibited content and manage members, with audit history.
**Evidence:** Three of the five exist and are audited. **Pin/unpin** — `pinMessage` (`src/features/channels/services/message.commands.ts:341-372`) writes `pinned_resource` and an audit row; authorization is by policy, requiring channel membership *and* staff in the channel's organization (`20260902002148:109-129`), and the error message names the rule when the policy refuses (`:358`). **Archive/restore** — `setChannelArchived` (`channel.commands.ts:187-227`), audited both ways, refusing the mandatory channel. **Remove prohibited content** — `deleteMessage` (`message.commands.ts:388-408`) is a **soft** delete that stamps `deleted_at` and preserves the row for evidence (comment at `:390`), audited as `message_deleted`; authorization is the `message_author_update` policy, now author-or-organization-admin (`20260902002148:174-178`).
**Gap:** (1) **There is no moderator role.** `channel_member.role` is documented as `member | manager` (`0002_communication.sql:45`) and `createChannel` sets `manager` for the creator (`channel.commands.ts:66`) — but `grep -rn "manager" supabase/migrations/` returns that one comment and nothing else: **no policy anywhere reads the column**. Every moderation action is gated on organization-level `staff`/`admin` instead, so "authorized moderators" means "any staff member, in any channel", and a channel owner who is not staff can moderate nothing. (2) **Lock is missing** — `reply_policy = 'disabled'` is the model for it but cannot be set (P0-GOV-01), and there is no posting freeze short of archiving the whole channel. (3) **Manage members is add-only** — no removal path exists (P0-GOV-02). (4) `unpinResource` (`message.commands.ts:374-386`) calls only `requireSession()` and writes **no audit row**, so unpinning is the one moderation action with no history.

### P0-GOV-04 — Message/file retention configurable at organization level
**Verdict:** Missing
**Requirement:** Message and file retention is configurable at organization level, with narrower legal/policy exceptions where approved.
**Evidence:** A capable retention engine exists and is organization-scoped — `retention_policy(organization_id, subject_key, retain_days, action, enabled)` with one policy per record type per organization (`supabase/migrations/20260828200241_retention_policies.sql:101-124`), a floor per subject enforced by trigger (`:136`), an off-by-default rule (`:110`), a nightly sweep (`src/features/jobs/services/handlers/apply-retention.ts`), and an admin editor that shows the affected count before anything is switched on (`src/app/(workspace)/admin/retention/page.tsx`).
**Gap:** **Messages and files are not governed by it.** `retention_subject` is a deliberate whitelist, and its five rows are `activity_event`, `notification`, `crm_interaction`, `export_job`, `audit_event` (`20260828200241:60-88`). `message` and `document` are absent, so channel history and uploaded files are kept indefinitely with no organization-level control — and because the whitelist is enforced by a foreign key (`:104`), an administrator cannot add them from the application; it requires a migration. This is the one requirement in the family where the machinery is built and simply not pointed at the two record types the requirement names. The "narrower legal/policy exceptions" half — a legal hold that overrides a policy — has no model at all; `retention_policy` has no exception, hold or scope column.
**Note:** Not a design accident worth criticising in itself: the whitelist-with-floors approach is the right one, and `apply-retention.ts` already exists to sweep whatever is added. Adding two `retention_subject` rows and their sweep clauses is the whole of the work.

### P0-GOV-05 — Auditability of channel governance events
**Verdict:** Partial
**Requirement:** Channel creation, privacy changes, posting-policy changes, membership overrides, moderation and message deletion are auditable.
**Evidence:** Four of the six are audited, and the two membership/moderation ones carry useful metadata. Creation — `channel_created` with `{privacy, type}` (`src/features/channels/services/channel.commands.ts:70-78`). Membership override — `channel_member_added` with `{user_id}`, written only after an explicit owner-or-admin check in the command as well as the policy (`:151-176`). Moderation — `message_pinned` (`message.commands.ts:360-368`) and `channel_archived`/`channel_restored` with `{name}` (`channel.commands.ts:215-224`, whose comment cites this requirement by number). Message deletion — `message_deleted` on a soft delete that keeps the row (`message.commands.ts:398-406`).
**Gap:** (1) **Privacy changes and posting-policy changes cannot be audited because they cannot be made** — no command writes `privacy`, `posting_policy` or `reply_policy` after creation (P0-ADM-02). This is not a missing audit call; it is a missing capability that takes the audit requirement with it, and it will not surface as a bug until someone tries to lock down a channel. (2) **Membership overrides are audited on only one of four write paths.** `channel_member` is inserted by `addChannelMember` (audited), `joinChannel` (`:84-99`, not audited), `createTeam` (`team.commands.ts:51-56`, not audited) and twice in `project.commands.ts:77,437` (not audited) — and `leaveChannel` (`:100-120`) records nothing either, so departures from a private channel leave no trace. (3) `unpinResource` is unaudited (P0-GOV-03).

### P1-GOV-06 — Guest boundaries
**Verdict:** Missing
**Requirement:** Read-only or limited guests can be restricted to **approved** channels and records, without discovering unrelated people or content.
**Evidence:** `guest` exists as a role (`supabase/migrations/0001_core.sql:11`) and is excluded from the staff and admin predicates, so the operational surfaces are closed to it — `supabase/tests/rls.sql:1196-1300` asserts a guest cannot read the audit trail, CRM organizations, report snapshots, background job runs, job runtime history, workflow executions, other people's email deliveries or rate-limit counters, and cannot rewrite a risk (`:688-697`) or record an opportunity (`:743-751`). Navigation hides the staff and admin destinations (`src/config/navigation.ts:87-100`).
**Gap:** There is **no guest scoping mechanism at all** — a guest is an ordinary member with the staff surfaces removed, which is not what this requirement asks for. Concretely: (1) **guests discover every person.** `/people` requires only `requireSession()` (`src/app/(workspace)/people/page.tsx:35`) and `membership_read` admits any active member of the organization (`20260818080439:105-107`), as does `can_read_profile` (`:63-79`) — so a guest sees the full directory with names, emails, titles and roles. (2) **Guests are not read-only.** `posting_policy = 'everyone'` resolves to `app.is_org_member` (`20260902002201:64`), and `channel_member_join` lets anyone join any public channel in their organization (`:71-90`), so a guest can join every public channel and post in it. (3) **There is no approved-channel or approved-record list** — no column, table or policy expresses "this guest may see these records"; `organization_membership` carries a role and a status and nothing scoping. The suite's own comment is candid about the design: "A guest belongs to the organization, so directory-level reads are expected" (`rls.sql:1193-1195`) — which is a coherent position, but it is the opposite of what P1-GOV-06 specifies.

## P0/P1-PPL — people

### P0-PPL-01 — People directory
**Verdict:** Partial
**Requirement:** Authorized users can find internal users by name, role, team, program, project and active status.
**Evidence:** `/people` (`src/app/(workspace)/people/page.tsx`) lists members with avatar, name, title, role badge and email, joined-ordered (`:39-45`), and deep-links to a highlighted person via `?person=` (`:88`, used by search results and `PersonDeepLink`). **By name** — global search has a `person` branch matching `full_name ilike` and returning `/people?person=<id>` (`supabase/migrations/0005_search_deeplink_fix.sql:59-64`); the RPC is `security invoker` (`:13`) so it cannot show a user someone may not read. **By team** — a chip row filters the table (`people/page.tsx:91-115`, `:69-74`). **By active status** — active and inactive are split (`:72-75`) with the inactive count shown to admins only (`:186`). **Role** is displayed with a label and tone per role (`:15-28`).
**Gap:** Three of the six axes are absent, and one is display-only. There is **no search box on the directory itself** — finding someone by name requires the global search page and a redirect back; `/people` accepts only `person` and `team` parameters (`:31-33`). **Role is not filterable** — it renders as a badge with no filter chip. **Program and project are not present at all**: `program_membership` and `project_membership` exist (`0001_core.sql:110,143`) but the page never queries them, so "find users by program" and "by project" cannot be done from the directory. Note also that the directory is visible to every active member including guests (see P1-GOV-06).

### P0-PPL-02 — Teams
**Verdict:** Partial
**Requirement:** Admins manage reusable teams/groups that can drive program access, channel membership, mentions and reporting.
**Evidence:** Teams are real and admin-managed: `team` and `team_member` (`supabase/migrations/0001_core.sql:76-89`), organization-scoped read with admin-only write (`20260818080439:117-124`), plus `app.can_read_team`/`can_manage_team` helpers (`:37-60`). `createTeam`, `addTeamMember`, `removeTeamMember` are all `isAdmin`-gated (`src/features/admin/services/team.commands.ts:18,64,88`) and surfaced in Admin → Teams as a per-person toggle (`src/app/(workspace)/admin/page.tsx:415-441`). Two of the four downstream uses work. **Mentions** — `@team-name` is expanded server-side into the individual members, intersected with the channel audience so a mention cannot notify someone who cannot see the message (`src/features/channels/services/message.commands.ts:62-97`). **Automation** — `notify_team` is a workflow action, resolving through `team_member` (`src/features/admin/services/workflow.runtime.ts:67-73`), with the team picker in the rule builder (`admin/page.tsx:495-502`).
**Gap:** The other two named uses do not work. **Channel membership is not driven by the team.** `createTeam` provisions a private team channel but seeds it with the creator alone (`team.commands.ts:34-57`); `addTeamMember` and `removeTeamMember` touch only `team_member` (`:64-99`). So team membership and team-channel membership diverge from the first person added, and removal from a team does not revoke the channel (see P0-GOV-02). **Program access is not driven by the team** — `program_membership` is keyed on `user_id` (`0001_core.sql:110-115`) with no team dimension, and nothing joins the two. **Reporting by team** does not exist: the only team filter in the product is the chip row on `/people`. Teams are also not editable or deletable once created — there is no `updateTeam` or `deleteTeam`.

### P0-PPL-03 — Role/access view per user
**Verdict:** Partial
**Requirement:** An admin can see one user's organization, program, project and channel memberships, and change their access, with audit history.
**Evidence:** The organization dimension is complete. Admin → Members shows every person's role, status and joined date with inline controls (`src/app/(workspace)/admin/page.tsx:193-260`), and both mutations are audited with before/after: `changeMemberRole` records `{from, to}` (`src/features/admin/services/admin.commands.ts:99-103`) and `setMemberActive` records `user_deactivated`/`user_reactivated` (`:149-156`), the latter also revoking live sessions globally (`:137-142`). Team membership is visible and changeable per person in Admin → Teams (`admin/page.tsx:415-441`). The section header cites this requirement by number (`:191`).
**Gap:** Three of the four dimensions are missing from the view. There is **no per-user page at all** — `/people?person=<id>` only scrolls a table row into view (`src/features/admin/components/person-deep-link.tsx:6-13`), so "a user's access" is assembled by eye from two tables on the Admin page. **Program, project and channel memberships are never shown**: `program_membership`, `project_membership` and `channel_member` are not queried by `/admin` or `/people` for a given person, so an admin cannot answer "what does this person have access to" or revoke a program or channel from here. And **team changes are not audited** — `addTeamMember` and `removeTeamMember` (`team.commands.ts:64-99`) write no `audit_event`, so the one access change beyond role and status that an admin *can* make leaves no history, which is the specific thing this requirement asks for.

### P1-PPL-04 — Workload context without surveillance
**Verdict:** Partial
**Requirement:** Authorized managers see assignments, due-soon/overdue work and availability references, without turning the tool into employee surveillance.
**Evidence:** The restraint half is done deliberately and well. `/people` computes one number per person — the count of open, unarchived tasks assigned to them (`src/app/(workspace)/people/page.tsx:77-80`) — and both the query and the column are gated on `session.isStaff` (`:45-56` and `:133-137,174-179`), so a volunteer or guest sees neither the data nor an empty column hinting it exists. The count deliberately excludes `completed`/`cancelled` and archived work (`:48-53`). Nothing tracks presence, activity, message counts, hours or last-seen anywhere in the codebase, which is the surveillance line this requirement is drawing.
**Gap:** The "assignments, due-soon/overdue" half is not in the manager's view. The directory shows a single scalar with no breakdown: no list of what those tasks are, no due-soon or overdue split, and no link through to them — the four-bucket overdue/today/this-week/later grouping exists only on `/my-work`, which shows the *viewer's* own work (`src/app/(workspace)/my-work/page.tsx`), not a report's. **Availability references are absent from the manager surface** — `vms_availability` is synced onto `user_profile` by the VMS job (`src/features/jobs/services/handlers/vms-sync.ts:80`) but `grep -rn "vms_availability" src/app/` shows it is never rendered anywhere, on `/people` or elsewhere (see P1-VOL-03). So of the three things a manager is meant to see, one is present as a bare count, one is missing and one is collected but not displayed.

## P0/P1-VOL — volunteers

### P0-VOL-01 — Volunteer system integration (link, don't duplicate)
**Verdict:** Partial
**Requirement:** The Hub links to the existing Volunteer Management System for volunteer identity, availability and assignment references, rather than duplicating the volunteer database.
**Evidence:** The "don't duplicate" half is honoured precisely. The Hub stores exactly three VMS-derived fields on `user_profile` — `vms_id` (`supabase/migrations/0008_spec_delivery.sql:9`, partially indexed at `:15-16`) and `vms_availability` + `vms_synced_at` (`0016_vms_sync_fields.sql:4-6`, availability constrained to three values) — and no volunteer records of its own. The sync job is careful about tenancy: it walks only connections with `status = 'connected'`, restricts every update to that connection's own active members, and matches on `vms_id`, so "a VMS response can never reach across a tenancy boundary" (`src/features/jobs/services/handlers/vms-sync.ts:26-90`); failures mark the connection degraded rather than leaving stale data looking fresh. `connectVolunteerSystem` refuses to record a connection it could not actually reach (`src/features/admin/services/integration.commands.ts:89-105`) and audits `vms_connected` (`:135-141`). Disconnect drops the VMS fields and explicitly does **not** delete Hub tasks, asserted as a contract (`src/features/admin/services/vms.ts:39-41`, `src/features/admin/tests/vms.test.ts:26-31`). Response parsing is fixture-tested and rejects incomplete identities (`vms.ts:8-37`).
**Gap:** **The pipeline has no input.** `linkVmsIdentity` (`integration.commands.ts:147-161`) is the only writer of `user_profile.vms_id`, and `grep -rn "linkVmsIdentity" src/` returns its own definition and nothing else — no component, page or dialog calls it. Since `vms-sync` matches on `.eq("vms_id", identity.vmsId)` (`vms-sync.ts:85`), and no `vms_id` can ever be set through the product, the job will match zero rows however healthy the connection is. The integration is complete, tested and unreachable. **There is also no link to the VMS**: nothing renders a URL to a volunteer's record in the source system, so "the Hub links to the VMS" is true only in the data-modelling sense.

### P0-VOL-02 — Simplified volunteer home
**Verdict:** Partial
**Requirement:** A volunteer sees assigned tasks/events, relevant channels, announcements, schedule, files, contacts and action buttons; admin, CRM and portfolio complexity is hidden.
**Evidence:** The hiding is done in three layers rather than one, which is what makes it trustworthy. **Navigation** — `visibleNav` filters by a typed `access` field, so Projects, Programs, Master Schedule, Relationships, Reports and Admin never render for a non-staff user (`src/config/navigation.ts:87-100`, `:42-84`). **Page composition** — the Home hero, portfolio pulse, health rollups, risky projects and unassigned-task lists are each wrapped in `session.isStaff`, with the comment citing this requirement (`src/app/(workspace)/page.tsx:148`, also `:150,206,297,356,506,562`), and the greeting subtitle changes to "Your assigned work, announcements, and upcoming schedule" (`:117-119`). **Data** — `task_read` admits a non-staff member only for rows assigned to them (`supabase/migrations/20260818081240:5-9`), so the "Organization board" a volunteer opens contains only their own work; the filtering is in the database, not the view. Everything the requirement lists as *visible* is reachable at member level: My Work, Board, Events, Channels, Messages, Announcements, Calendar, Meetings, Documents, People, Saved, Inbox, Requests.
**Gap:** There is no volunteer *home* — there is the staff home with six sections removed, which reads as an emptier version of somebody else's page rather than a page designed for the reader. More concretely, **the simplification does not distinguish volunteer from guest**: `visibleNav` takes only `{isAdmin, isStaff}` (`navigation.ts:87-90`), so both roles get the identical 14 destinations, and a volunteer sees `/requests`, `/inbox` and the full people directory on the same footing as anyone else. "Contacts" is served by the org directory rather than anything volunteer-relevant, and the volunteer's own VMS availability and assignments are not shown anywhere (P0-VOL-01, P1-VOL-03).

### P1-VOL-03 — Availability signal at assignment time
**Verdict:** Partial
**Requirement:** Where the integration permits, authorized staff can see volunteer availability when assigning events or tasks; the source system stays authoritative.
**Evidence:** The data is modelled and kept fresh, and the authority boundary is respected. `user_profile.vms_availability` is constrained to `available | unavailable | unknown` and defaults to `'unknown'`, with `vms_synced_at` alongside it (`supabase/migrations/0016_vms_sync_fields.sql:4-6`) — three states and a timestamp, not a copy of the VMS calendar, so the Hub cannot drift into being the authority. `vmsSync` refreshes it nightly for linked profiles only, per connection and per organization (`src/features/jobs/services/handlers/vms-sync.ts:76-90`), and marks the connection degraded on failure rather than serving stale data as current (`:17`). The job's own comment states the boundary: "The VMS owns the source data; the Hub stores only a linked external id and the current availability needed for assignment decisions" (`:8-11`).
**Gap:** **It is never shown at the point of assignment, or anywhere else.** `grep -rn "vms_availability" src/` returns exactly one hit — the `update` inside the sync job. The event role-assignment dialog offers a plain person picker with no availability column, badge or sort (`src/app/(workspace)/events/[id]/page.tsx:186-194`), and the task assignee pickers are the same `options.people` list. So the signal is fetched, stored, constrained and timestamped, and then no staff member ever sees it — the requirement's whole purpose. Compounding it, no `vms_id` can be set through the product (P0-VOL-01), so `vms_availability` is `'unknown'` for every row in practice. Rendering the badge would be a small change; making it non-empty needs the linking UI first.

The shape of the family is consistent enough to be worth stating plainly: **the
database is in much better condition than the product built on top of it.**
Almost every Partial here is the same pattern — the table, the column and the
policy exist and are correct, and the command or the screen that would use them
was never built. `scopes`, `vms_availability`, `reply_policy`, `is_mandatory`,
`channel_member.role`, `feature_flag` and `audit_event.result` are all modelled
and all dead. That is a better problem to have than the reverse, but it means
readiness read from the schema will consistently overstate readiness in use.

The security work done today was real and is verified below, but it was
reactive — it fixed what a failing assertion happened to reveal. The three
findings here were all found by looking somewhere no assertion points.

### The three findings a maintainer should see first

1. **Invite-only sign-up is enforced only in the browser, and an uninvited
   self-registrant is provisioned as active `staff`.** `signup_allowed` is
   called from a `"use client"` component
   (`src/app/(auth)/sign-up/sign-up-form.tsx:23-35`); the trigger that actually
   grants the membership never consults it and falls through to `'staff'`
   (`supabase/migrations/0003_operations.sql:381-389`). A direct `auth.signUp`
   with the public anon key therefore yields staff access to projects,
   programs, CRM, reports, every task and every public channel. The
   `before_user_created` hook that belongs here is commented out in
   `supabase/config.toml:284-287` and `enable_signup = true` at `:182`. Two
   things compound it: `docs/runbooks/deployment.md:24-26` assures the operator
   that "the app also enforces invite-only via `signup_allowed`", which is not
   true, and `supabase/tests/rls.sql:1313-1317` asserts the *predicate* returns
   false while nothing asserts that anything consults it — a green check
   sitting directly over the gap. **This is the one item on this list that
   should not wait.** (AUTH-007, cross-referenced from AUTH-002.)

2. **The `documents` storage bucket has two role-only policies using the
   unscoped helpers, and the new anti-regression assertion cannot see them.**
   `"documents delete for staff"` is `bucket_id = 'documents' and
   app.is_staff()` with no join to `document`
   (`supabase/migrations/0006_documents.sql:74-76`), so any staff member of
   *any* organization can delete any object in the shared bucket given its
   path; `"documents upload for active members"` is unscoped the same way.
   These are the only three `storage.objects` policies in the repository and
   both scoping migrations missed them — and the standing check that was added
   to stop exactly this filters `pg_policies` on `schemaname = 'public'`
   (`supabase/tests/rls.sql:1344`), so `storage` is a blind spot in the guard
   rail as well as in the fix. Widening that one predicate is a one-line
   change that turns an invisible gap into a failing test. (SEC-007, AUTH-003.)

3. **Channels cannot be governed after they are created, and nobody can be
   removed from one.** No command writes `privacy`, `posting_policy`,
   `reply_policy` or `is_mandatory` after `createChannel`; `reply_policy` is
   never set at all, so every channel runs on the `'normal'` default; and every
   `channel_member` write in `src/` is an insert or a *self*-delete
   (`channel.commands.ts:100-120`), so an admin has no path to revoke someone's
   access even though the RLS policy would allow it. Team membership does not
   drive team-channel membership either — `removeTeamMember` touches only
   `team_member` (`team.commands.ts:84-99`) — so a person removed from a team
   keeps reading its private channel indefinitely. Four requirements fail on
   this one cluster (P0-ADM-02, P0-GOV-01, P0-GOV-02, P0-GOV-05), and it is the
   gap most likely to be discovered by a real incident rather than by a test.

### Where the code is better than the documents claim

Recorded because an understated readiness is an error too.

- **No `SECURITY DEFINER` RPC is reachable by a signed-in user.** All four
  public RPCs granted to `authenticated` are `SECURITY INVOKER` and so run
  under the caller's policies; every definer function is `service_role`-only,
  with the two deliberate narrowings written down
  (`20260820180000_tighten_definer_grants.sql`). Independently confirmed:
  **75 tables, 75 `enable row level security`**, and exactly one `using (true)`
  policy in the schema — immutable reference data.
- **AUTH-009 is genuinely met**, which no document claims. ~20 centralized
  database predicates, mirrored by typed `isAdmin`/`isStaff` helpers carrying
  149 checks, against **12** raw role-string comparisons in all of `src/` —
  every one of them a real `owner` special case or a non-role value test.
- **Retention (P1-ADM-06) is the strongest admin surface in the product** and
  `docs/production-readiness-audit.md` does not say so: a whitelist with a
  per-subject floor enforced by trigger, policies created switched off, and an
  editor that shows what a rule *would* delete tonight before it is enabled.
- **The exports bucket is an exemplar of SEC-007** — no `authenticated` policy
  at all, authorization done with the *user's* client, expiry tested against
  the clock rather than the status, the download counted before the URL is
  minted, and a 120-second signature. The `documents` bucket should be brought
  to it, not the other way round.
- **P1-PPL-04's restraint is deliberate and correct.** No presence, activity,
  message-count, hours or last-seen tracking exists anywhere. The manager view
  is one number, staff-gated at both the query and the column.
