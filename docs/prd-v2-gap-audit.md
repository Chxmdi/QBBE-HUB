# PRD v2.0 implementation gap audit

Reviewed: 2026-09-07. Source: `QBBE-Operations-Project-Hub-PRD-v2.0.docx`, version 2.0, prepared July 30, 2026, supplied by the user. This is a static comparison of its acceptance criteria with the repository, not a production certification. No application code or deployed configuration was changed. Tests could not run in this checkout because dependencies are absent.

The attached PRD is a different document from the later master-spec build brief. Its requirement IDs must not be equated with identically named IDs in the existing coverage matrix: for example, this PRD's P0-PRJ-03 is project overview, not milestones. The document's instructions are treated as requirements to assess, not authorization to implement or deploy changes.

Subsequent implementation is tracked in [the acceptance matrix](acceptance-matrix.md)
and [implementation progress](implementation-progress.md). This dated audit
is a historical baseline, not the current completion status.

## Scope correction

The PRD explicitly excludes built-in chat and highly configurable enterprise automation from the initial release (§5.2). Gmail inbox functionality, Slack-style channels, extensive workflow automation, and the later brief's other additions do not substitute for the PRD's core acceptance criteria. Preserve existing features, but do not count their presence as proof that the core workflow is complete. Advanced integrations are phased (§24); VMS integration is a build-readiness decision (§27), not a numbered P0 acceptance criterion.

Statuses below mean **Partial** (some relevant implementation exists), **Missing** (no corresponding implementation found), and **Unverified** (needs execution or external evidence). This is a gap register, not a claim that unlisted requirements have passed acceptance.

## Verification and operational work (§22–27, appendices)

1. **Security:** test restricted program/project membership through UI, direct API, search, realtime and exports; fix the export signing authorization issue before pilot use. Recheck delivery after access revocation and account deactivation.
2. **Acceptance automation:** implement/run the eight §25.2 scenarios (project ownership, task lifecycle, access boundary, agenda workflow, comment notification, dashboard roll-up, CRM follow-up and deactivation). Existing public-route CI and mostly-owner QA do not cover these completely.
3. **Accessibility/performance:** run authenticated keyboard/mobile/WCAG checks and normal-scale timing tests against 15–50 users' realistic data; verify Chrome, Safari, Edge and Firefox. Address hard task-list caps and unpaginated exports; no current performance certification is established here.
4. **Real email:** verify QBBE sender/reply-to/support ownership, delivery, actionable context, secure deep links, category suppression and deduplication. Real transport code exists; live setup is unverified.
5. **Reliability:** validate visible/retriable saves and integrations, production error capture and backups before real pilot data. Perform a restore drill before organization-wide rollout. Runbooks alone are not execution evidence.
6. **Deployment:** establish/verify QBBE-owned accounts, environments, secrets, domain, protected checks, deployment and recovery procedures. Current repository launch gate marks production evidence unverified; this audit did not inspect remote settings.
7. **Privacy and rollout:** name product/privacy owners; approve prohibited-data/retention/incident procedures; select one program and 3–7 pilot users; collect days 3/7/14 feedback and a go/no-go decision. These are organizational actions, not missing UI components.
8. **Success metrics:** establish measurement for activation, weekly adoption, ownership/date coverage, update freshness, meeting-action completion, notification quality and 90-day retention. General dashboard counts are not this acceptance evidence.
9. **Documentation:** keep this PRD's IDs separate from the later brief's IDs, reconcile coverage against actual acceptance criteria, and retain a versioned authoritative source or approved readable transcription. Do not claim a completion percentage from screen counts.

## Recommended implementation sequence

1. Scoped membership authorization, account recovery and export security.
2. Reusable contextual comments and immediate action notifications.
3. Project/task role management, milestone fields, mandatory active-state rules and archive/restore.
4. Meeting/agenda context and lifecycle; leadership dashboard and trustworthy health signals.
5. Remaining P1 reporting, CRM links, cadence, templates, preferences and recurrence.
6. Automated acceptance, real email, backups/restore and a focused pilot; defer P2 until adoption warrants it.

Verdict: **P0 implementation remains incomplete; production/pilot acceptance is not established.** This supersedes the earlier implication that the remaining work was predominantly integration setup and production verification.
