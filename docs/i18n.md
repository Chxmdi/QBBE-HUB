# French and English interface (#141)

The Hub speaks English (`en`) and Quebec French (`fr-CA`). English is the
default. Every screen is translated; `tests/e2e/translated-workspace.spec.ts`
and `translated-finance.spec.ts` fail if English interface text comes back on
any of them in French.

## How a request picks its language

`getLocale()` in `src/lib/i18n/server.ts` decides once per request, in this
order, without any database or Auth call:

1. The `qbbe-locale` cookie.
2. The browser's `Accept-Language` header. Any French variant becomes `fr-CA`.
3. English.

The person's saved choice, `user_profile.locale` (set in **Settings**), is the
record. Saving it also writes the cookie. On a device that has not seen the
choice yet, `LocaleSync` in the workspace layout copies it into the cookie and
re-renders once. The language switch on the sign-in screens sets only the
cookie.

Do not read the session in `getLocale()`: it runs in the root layout and in
every page's metadata, and doing so made every signed-in page noticeably
slower.

The root layout sets `<html lang>` from it and hands it to client components
through `I18nProvider`.

## Translating a screen

1. Add the English text to the area's catalogue. Each screen area has a pair
   of files, `<area>.en.ts` and `<area>.fr-CA.ts`, in
   `src/lib/i18n/messages/workspace/` (finance areas in
   `src/lib/i18n/messages/finance/`). Each area owns the top-level namespaces
   listed at the top of its file (`work` owns `home`, `myWork`, `board`,
   `tasks` and `dashboard`, for example); nest new keys inside them. Shared
   words (`common`, `nav`, `ui`, …) stay in `messages/en.ts`. Placeholders are
   written `{name}`; for counts, use a pair of keys (`…One` / `…Other`).
2. Add the same key to the French file. It is typed against the English one,
   so a missing or misspelled key fails `npx tsc --noEmit`, and
   `src/lib/i18n/i18n.test.ts` fails on an empty string, a placeholder that
   differs between the two, a French string that is just the English copied
   across (words spelled the same in both go in its allowlist), or two areas
   claiming the same namespace.
3. Replace the literal:
   - Server component: `const t = await getT();` then `t("screen.key")`.
   - Client component: `const t = useT();` from `@/lib/i18n/client`.
   - Page title: replace `export const metadata` with a `generateMetadata`
     that calls `getT()`.
4. Dates, times, numbers and money: use `getFormatters()` (server) or
   `useFormatters()` (client). They give `26 sept. 2026`, `14 h 30` and
   `1 234,56 $` in French. The helpers in `src/lib/utils.ts` also take an
   optional trailing `locale` argument.

Code in services and server actions can call `getT()` too: outside a
request (unit tests, scripts) it falls back to English. Anything sent to a
person — emails, notifications, reminders — uses that person's
`user_profile.locale` with `createTranslator(locale)`, not the request.

Values stored as codes (statuses, roles, categories) stay codes in the
database and are turned into labels when shown. Text people typed is data and
is never translated. Activity-feed sentences (`activity_event.summary`) are
still stored as English sentences and shown as stored; rendering them from
their verb and record at display time is a follow-up.

Navigation labels are translated by href in `src/lib/i18n/navigation.ts`, so
`src/config/navigation.ts` stays a plain list. A new navigation entry without a
translation there shows its English label.

## Review

The French text is a first draft. It must be reviewed by a fluent French
speaker named by QBBE before the switch-over. Style followed: OQLF usage
(« courriel »), 24-hour clock, a non-breaking space before a colon and none
before `?` or `!`.
