# AGENTS.md

## Cursor Cloud specific instructions

QBBE Hub is a single Next.js 15 (App Router) app backed by Supabase (Postgres +
Auth + RLS + Realtime). There is one product/service to run. Standard scripts
live in `package.json`; README.md and `docs/runbooks/` cover the rest — prefer
those over duplicating here.

### Services and how to run them

- Web app (dev): `npm run dev` → http://localhost:3000. Requires `.env.local`
  pointing at a Supabase backend (see below). The app is auth-gated: every route
  except `/sign-in`, `/sign-up`, `/auth/*` redirects to `/sign-in` until you are
  signed in.
- Local Supabase (Docker-based): provides Postgres/Auth/Realtime for real
  end-to-end use. Studio is at http://localhost:54323, the API at
  http://127.0.0.1:54321, and the Mailpit test inbox at http://localhost:54324.

### Startup on a fresh VM (non-obvious — do this before `npm run dev`)

Docker and the Supabase CLI are preinstalled in the environment snapshot, but
the Docker daemon does not auto-start and Supabase must be started manually:

1. Start Docker: `sudo service docker start` (once per boot).
2. Start Supabase from the repo root: `sudo -E supabase start`. The daemon
   socket is root-owned, so Supabase/Docker commands need `sudo` (the `ubuntu`
   user is in the `docker` group, so a fresh login shell can drop `sudo`).
3. Ensure `.env.local` exists (it is gitignored). Copy `.env.example` to
   `.env.local` and set the local values. The local anon key is the standard
   Supabase demo key and is stable across restarts:
   - `NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:54321`
   - `NEXT_PUBLIC_SUPABASE_ANON_KEY=` (get it via `sudo -E supabase status -o env | grep ANON_KEY`)
4. `npm run dev`.

### Database / migrations / seed

- `sudo -E supabase db reset` recreates the DB and re-applies
  `supabase/migrations/*.sql` in order. Use it to get a clean state.
- After adding or changing a migration, regenerate the database types on a
  freshly reset local database: `npm run db:types`, and commit
  `src/types/database.ts`. CI fails (`npm run db:types:check`) when they no
  longer match. Only the service client is typed so far
  (`SupabaseClient<Database>`); the session clients follow module by module.
- The **first** sign-up bootstraps the workspace (creates the organization,
  makes that account Primary Owner, provisions the mandatory `#announcements` +
  `#general` channels). Later sign-ups join as Staff. So a clean DB + first
  sign-up is the fastest "hello world".
- Auto-seed is intentionally disabled in `supabase/config.toml` because
  `supabase/seed/seed.sql` requires a signed-up user to already exist. Run it
  manually after the first sign-up if you want synthetic data:
  `sudo -E docker exec -i supabase_db_workspace psql -U postgres -d postgres < supabase/seed/seed.sql`.

### Migration versions

- Applied migrations carry versions dated weeks ahead of the calendar.
  `supabase migration new` names a file with today's timestamp, which would
  sort before them: the hosted `supabase db push` refuses it, and
  a fresh `db reset` would apply it out of order. Until the calendar passes
  the newest version on `main`, rename every new migration to the newest
  version on `main` plus one step (for example `20261116010000_...` after
  `20261115020000_...`). Never use `db push --include-all`, and never rename
  or delete a migration that has been applied anywhere.
- `tests/unit/migration-filenames.test.ts` enforces this against the frozen
  list in `tests/unit/migration-baseline.json`. Do not add entries to that
  list to make the test pass.

### Non-obvious gotchas

- `auto_expose_new_tables = false` is set in `supabase/config.toml`, matching
  hosted projects. The API roles (`anon`, `authenticated`, `service_role`) get
  nothing on a new table, view, sequence or function in `public` unless the
  migration grants it. `20261119100000_explicit_api_grants.sql` (generated by
  `scripts/db/generate-grants.mjs`) grants everything created before it and
  revokes the automatic default privileges. Every later migration must add its
  own `grant ... to authenticated, service_role` (tables, views, and the sequence
  of any serial column), and `revoke all on function ... from public, anon`
  before granting EXECUTE: Postgres lets every role execute a new function
  otherwise;
  `tests/unit/migration-grants.test.ts` fails otherwise. A missing grant shows
  up as `permission denied for table ...`, and on a signed-in page as a silent
  redirect back to `/sign-in`. Signed-out visitors (`anon`) may read only
  `published_page`; their other queries are refused rather than returning no
  rows. After changing the flag: `supabase stop`, `supabase start`,
  `supabase db reset`.
- Local Supabase disables email confirmation (`auth.enable_confirmations =
  false`), so sign-up immediately returns a session — no inbox step needed.

### Lint / test / build

- Standard commands are in `package.json`: `npm run lint`, `npm run typecheck`,
  `npm test` (Vitest), `npm run build`.
- Public-route Playwright a11y suite (no DB needed, mirrors CI): build, serve,
  then `npx playwright test public-routes`. Playwright uses the browser from
  `npx playwright install` unless `QA_CHROME_PATH` is set (Cursor Cloud
  sandbox only). GitHub Actions CI does **not** set `QA_CHROME_PATH`.
- Database/RLS tests: `npm run test:db` against local Supabase
  (the `postgres` database on `127.0.0.1:54322`, the local stack's default
  `postgres` user). Requires
  `supabase start`. Falls back to `sudo docker` when the daemon socket is
  root-owned (typical on this VM).
- Unchecked database writes: `node scripts/ci/check-unchecked-writes.mjs`
  (also run by `tests/unit/unchecked-writes.test.ts`). Every
  `await x.from(...).insert/update/upsert/delete(...)` must read its
  `{ error }`, and so must `.rpc(` calls. Older ones are counted per file in
  `scripts/ci/unchecked-writes-allowlist.json`; the count must match exactly, so it can only go down.
  After fixing some, run the script with `--update`. Exports of personal or
  financial data write their audit row with `recordAudit` from
  `src/lib/audit-write.ts` and refuse the file if it fails.
- Background jobs: every job runs through `POST /api/jobs/<name>` with the
  header `x-job-secret: $CRON_JOB_SECRET`; `GET` answers 405 and a missing or
  wrong secret 403. In production pg_cron calls it (docs/runbooks/jobs.md has
  every job, its schedule and what it does). To run one by hand:
  `npm run jobs:run -- <name>` with `CRON_JOB_SECRET` set. `/api/jobs/*` is
  excluded from session middleware.
- Email: `drain-notifications` sends through Resend when
  `EMAIL_PROVIDER_API_KEY` is set, through SMTP when `SMTP_HOST` is (locally,
  Mailpit at `127.0.0.1:54325`, UI `:54324`), and otherwise only records it.
- Gmail/VMS: OAuth Connect syncs Gmail metadata immediately when credentials
  exist; `google-sync` keeps Gmail, Calendar and Drive current every 15
  minutes. VMS Connect probes the API and refuses if it is unreachable.
- Deactivated members are sent to `/account-inactive`, not a sign-in loop.
- After the first organization exists, an account can only be created from an
  invitation link (`/sign-up?invite=<secret>`), and the membership waits for
  the address to be confirmed. The database enforces it in
  `app.handle_new_user` (SEC-001,
  `supabase/migrations/20261116010000_invitations_need_their_token.sql`);
  the sign-up page's checks only choose which screen to show.
- Channel history loads the **newest** page first (`CHANNEL_HISTORY_PAGE_SIZE`);
  use **Load older messages** for prior pages. A `.limit(N)` with
  `created_at` ascending would have returned the oldest N instead.
- Opt-in hello-world Playwright: `npx playwright test tests/e2e/hello-hub.spec.ts`
  (not in CI). Uses `qa-owner@example.com` / `QaTest!2026`.
